## Context

RAG 查詢的 prompt 由 `src/services/retrieval.js` 的 `buildPrompt()` 組裝，內容包含：固定指令、檢索到的 chunks、完整 NPDS 文件目錄、使用者問題。當 LLM 無法從 chunks 回答時，會依目錄建議使用者上傳文件。

問題在於 prompt 從未包含「哪些文件已上傳」的資訊，且文件以 `docId = filename` 識別。因此使用者已上傳 C560（檔名任意），系統仍建議上傳 C560。修正方向：以 **NPDS 編號**為文件身分，把「已上傳編號」注入 prompt，指示 LLM 排除這些編號。

已具備的基礎：`vectorStore.listDocuments(projectId)` 可回傳該專案所有文件的 `{ phase, docId }`；前端已有從檔名擷取編號的正則（`C([1-7])\d{2}`）可參考。

## Goals / Non-Goals

**Goals:**
- 查詢時把已上傳文件的 NPDS 編號集合「從注入 prompt 的目錄中移除」，使 LLM 無從建議已上傳編號
- 編號比對以「編號為主、檔名不重要」：同編號即視為已上傳，不分大小寫
- 既有「找不到答案時建議具體文件」的行為維持不變，僅排除已上傳編號
- 比「另附已上傳清單」更省 token：上傳越多、目錄越短

**Non-Goals:**
- 不改 `docId` 的儲存方式（仍是檔名），只在查詢時「解讀」出編號
- 不做檔名與內容是否相符的驗證（使用者宣稱編號即採信）
- 不另外在 prompt 附一份「已上傳清單」並指示排除（改為直接從目錄刪除，更省 token 且更可靠）
- 不改前端

## Decisions

### 1. 編號擷取：以正則從 docId（檔名）取出 NPDS 編號

**決定**：新增工具函式 `extractNpdsCode(name)`，以正則 `/C[1-7]\d{2,}/i` 擷取檔名開頭的 NPDS 編號，回傳大寫字串（如 `C560`、`C3081`）；取不到則回傳 `null`。

**理由**：NPDS 編號格式為 `C` + 階段碼(1–7) + 至少兩位數字，且有四位數編號（如 C3081、C3082）。用 `\d{2,}` 涵蓋三位與四位。統一大寫以利去重比對。前端既有正則只取三碼（為了判 phase），這裡需要完整編號，故另寫一個。

---

### 2. 在 `answer()` 取得已上傳編號集合

**決定**：在 `answer()` 進行檢索後，呼叫 `vectorStore.listDocuments(projectId)`，將每個 `docId` 經 `extractNpdsCode` 轉換、去除 `null`、去重，組成已上傳編號集合，傳入 `buildPrompt`。

**理由**：`listDocuments` 已存在且回傳整個專案的文件清單，無需新增 DB 查詢。以 Set 去重，順序不重要。

---

### 3. 從目錄移除已上傳編號（而非另附清單）

**決定**：`formatCatalogForPrompt(excludeCodes)` 新增可選參數 `excludeCodes`（Set，大寫編號）。輸出時跳過 `code` 落在 `excludeCodes` 的文件項；若某階段所有文件都被排除，則該階段標題也一併略過。`retrieval.js` 把已上傳編號集合傳進去。

**理由**：目錄在 prompt 中的唯一用途就是「給 LLM 拿來建議上傳」（明寫「不作為回答資料來源」）。已上傳的編號從目錄中消失後，LLM 根本看不到、無從建議——比「附清單 + 指示排除」更可靠（不靠 LLM 服從），也更省 token（上傳越多目錄越短，而非越長）。

---

### 4. 以「目錄即唯一建議來源」為前提，不需額外指示或過濾

**決定**：不在 prompt 另加排除指示，也不在後端對建議文字做事後過濾。

**理由**：既有 prompt 已要求 LLM「根據下方的 NPDS 文件目錄」建議文件，建議來源被約束在目錄內。只要目錄不含已上傳編號，建議自然不含——機制單一、可理解。若日後發現 LLM 仍從目錄外（自身知識）亂建議，再評估加後端過濾。

## Risks / Trade-offs

- **檔名沒有編號** → `extractNpdsCode` 回傳 `null`，該文件不納入已上傳編號集合，目錄不會被刪到該編號，等於回到現狀（不會更糟）。使用者若要被正確識別，檔名需含編號——與系統「以編號為主」的前提一致。
- **編號擷取誤判** → 若檔名碰巧含 `C[1-7]` + 數字但非真正 NPDS 編號，可能誤刪目錄中某編號 → 該編號縱使未上傳也不會被建議。正則限定 `C[1-7]\d{2,}` 已大幅降低誤判面；可接受。
- **LLM 從目錄外建議** → 目錄已不含已上傳編號，但 LLM 理論上仍可能憑自身知識提到某編號。既有 prompt 已將建議來源限定為「下方目錄」，風險低；必要時未來加後端過濾。
- **token 影響** → 為正向：移除已上傳項使目錄變短，上傳越多省越多。
